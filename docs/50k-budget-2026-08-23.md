# The 50,000 chunks/s budget — what every per-chunk cost is allowed to be

## The arithmetic

Cold start must load **164,733 chunks**. At 50,000/s that is **3.3 s**, which is
the owner's "a few seconds". Today we measure **7,023/s and 23.5 s**.

**We need 7.1x.**

The game thread gets **5,000 ms per 5-second window**. At 50,000/s a window
carries **250,000 chunks**. So the TOTAL per-chunk game-thread budget is:

        5,000 ms / 250,000 chunks = 0.020 ms/chunk   (20 microseconds)

and that is the budget for EVERYTHING on the game thread combined, at 100%
occupancy. A sane target leaves room for the rest of the game:

        BUDGET: 0.008 ms/chunk total game thread  (40% occupancy)

## Where we actually are (measured 2026-08-23, `ahead-on` / `gp-ctl2`)

| stage | per chunk now | per-window at 50k/s | verdict |
|---|---|---|---|
| **apply** | 0.054 ms | **13,500 ms** | **2.7x OVER the whole window** |
| **submit** (post-cap) | 0.005-0.018 ms | 1,250-4,500 ms | **at or over budget alone** |
| submit (pre-cap, contended) | 0.144 ms | 36,000 ms | fixed by `-VoxelDispatchAheadCap` |
| recompute | ~250 ms/window | scales with SPAN, not rate | grows as Span^2 with 8-10 km rings |

**Two blockers, both arithmetic, neither yet solved:**

1. **Apply must get ~10x cheaper.** At 0.054 ms/chunk it alone needs 13,500 ms of
   a 5,000 ms window. The amplifier-column fix (`-VoxelApplyFast`) removes
   ~200-350 ms/window, which is real but is NOT this. Target: **<= 0.005 ms/chunk.**
2. **Submit must get ~5x cheaper.** 0.005-0.018 ms/chunk x 250,000 = 1,250-4,500 ms.
   Target: **<= 0.002 ms/chunk.**

## The property that actually decides it

Per-chunk cost is the wrong thing to optimise past a point — the thing that makes
50k reachable is work that is **FLAT IN N**: fixed per tick regardless of how many
chunks. The worklist proved the shape is available (per-chunk GPU submissions
5 -> 0, spine constant 11/tick). Anything still paid per chunk on the game thread
is a term in the 0.020 ms budget above; anything moved to per-tick is free.

**Ask of any proposed fix: does this reduce the constant, or does it remove the
term?** Removing the term is worth 10 of reducing the constant.

## What is NOT the blocker (measured, do not re-litigate)

- **The GPU.** Peak observed 14,632/s vs the CPU control's 10,291/s, and GPU
  compute sits ~1-2% utilised. Silicon was never the constraint.
- **The in-flight cap** (`cap=288` = `JobsInFlightPerCore` 8 x 36 cores). It reads
  like the ceiling — `exitCap` dominated `passes` — but results were backing up
  90,000 deep behind a starved drain. Raising it makes things WORSE. Check
  `drained` before believing any cap reading.
- **The manager tick.** `gpuMgrTickMs` is 12-47 ms against a 1,445 ms loop, 1-3%.
- **The fine-tile gate.** `rejFine = 0` in every window of every leg.
- **Render-thread backpressure.** `enqDisp/enqPoll ~ 0`.

## Standing traps that have cost retracted findings
- `grep | tail -1` lands on the post-flight linger window and reads all zeros.
  Four retractions. Use `tools/leg-summary.sh`; confirm `dispatched>0`.
- A counter reading a clean zero on the marcher path is usually an instrument
  outside the path, not an absence of cost. Twelve found this session.
- A value OBSERVED is not a limit IMPOSED. Read the constant, not the symptom.

## THE CEILING LADDER (assembled 2026-08-23 late, from four agents' measurements)

50,000 chunks/s is not blocked by one thing. It is blocked by a **ladder of
constants**, each sized for an earlier system, each invisible until the one below
it is lifted. Every rung below is measured, not estimated.

    rung  constant                            value   binds at      owner
    ----------------------------------------------------------------------------
     1    voxel.Stream.MaxAppliesPerFrame       192    ~4,000/s      apply agent
     2    MeshBatchCap (under -VoxelGpuPrimary)  64    ~3,840/s      gpujobmgr
     3    voxel.Stream.ApplyBudgetMs            6.0ms  ~6,000/s      apply agent
     4    kMaxResultDrainsPerFrame             1024    ~21,500/s     apply agent
     5    Worklist Write-triple group limit     442    ~26,520/s     worklist agent
          (65,535 D3D groups / 148 per record)   rec/tick
     6    per-chunk apply cost               0.021ms   ~105% of a    apply agent
          (2,381 applies/tick x 0.021 = 50ms)         21 Hz thread
     7    tick rate itself                    ~21 Hz   multiplies    unowned
          (every doubling halves the per-tick cap required)          every rung

**Rungs 1 and 2 bind TODAY at ~3,000-4,000/s measured.** Nothing upstream can show
up in a throughput number until they move: `queueEmpty = 0` in every filling
window, so the producer has never been the limit.

### Rung 1 is a COUNT, not a cost — proved by an unread instrument
`Voxel apply stages` has printed the drain loop's exit attribution since Wave S0.
Exit counts sum EXACTLY to `ticks` with `stale=0`, so it is a complete census:

    win ticks | qEmpty wall cntCap drnCap | drained | appl/tick
      3   107 |      0   30     77      0 |  15816  |   147.8
      7   107 |      0   29     78      0 |  16028  |   149.8

`countCap` ends 65-76% of ticks, and a countCap tick delivers exactly 192 — so
**93.5% of all applied chunks come from ticks stopped by that number.**
Throughput is literally `192 x tickRate`.

### Rung 2's justification was removed by someone else's fix
`MeshBatchCap`'s own comment says it is NOT a capacity limit: it is a burst
limiter protecting **render-thread pass setup** (32/64 -> 367 hitches vs 4/8's 8).
**Worklist stage 6 took a claim-fed chunk's brick passes to ZERO.** The per-chunk
reason for the cap is exactly what the fusion removes — and this file already
accepted that same argument once, at Tier B.1. Fix authored: a predicted
pass-free job draws its own allowance bounded by the worklist's per-flush consume
budget. 256 -> 15,360/s.

### What is NOT on the ladder
The per-chunk terms in `VoxelGpuMeshJobManager` are **finished**, and the agent
declined to ship the obvious fix on arithmetic: the whole Submit half is
0.44 us x 250,000 = **110 ms = 2.2%** of a window, and its largest single term
(`MakeShared<FJob>`) is **1.3%**. A hand-maintained free-list whose one missed
field leaks a stale value into the next chunk is not worth 1.3%. Recorded so
nobody re-derives it.

### The one lead that DELETES work rather than shaving it
`poolReplaced = shellsTaken - residentDelta`. On a cold fill with `evictions=0`,
each one is **a chunk generated over itself** — wasted submit, shell, graph,
claim and delivery. Whole chunks, not microseconds, and flat in N. Derived from
two integers the reval skip already reads.

## THE RULE THIS LADDER TEACHES
Every rung looked fine from every angle until the rung below it was lifted. A cap
at 54% occupancy does not *look* binding. **Do not lift more than one rung per
leg** — three caps in series make a throughput number unattributable to any of
them, which this codebase already documents for `GpuMeshInFlight`. And at every
rung, the failing reading must be stated first: **if lifting it does not move
`drained/s`, that rung was not the bound — revert, do not keep raising.**

1. **`claimverify checked` is above its own ceiling.** It grew 8,393,231 in a

2. **`unclaimed` was never broken — it was reading exactly this.**
   `1,121,101 shells − 0 stolen − 1,581,286 claims − 182,979 claimFails =

   the exhaustion, not the reverse** — which is the opposite of how it reads.

Falsifiable, and stated as such: with the fix `gpuClaimed == hostStaged == conv`,

## RUNGS 5 AND "FLATNESS" BOTH CLEARED PAST THE GOAL (authored, not yet built)

### The band-edge exclusion was a FALSE gate -- "derived, not verified" again

A job carries **two** region requests. `Job->Region` is the 48x48x6 **mesh**
region (one brick of halo) that produces the footprint band. `Job->BrickRegion`
is the halo-free 32x32xN region the worklist actually converts, and the record is
built entirely from it -- where `ApplyBrickRegionShape` sets `OutReq.BandEdge = 0`
**unconditionally**.

So the append gate `if (Job->Region.BandEdge != 0) continue;` **tested a field the
converted chain never reads.** It was copied from the LEAN gate, where testing
`Region.BandEdge` is correct because that decision is about the mesh-region graph.
A band chunk's brick region is byte-for-byte the same shape as a lean chunk's.

Checked rather than assumed: `AddRegionPasses`' column-feed checkf holds by
construction on `BrickRegion`; the poll path's `bNeedBand` gate is untouched; and
the flush graph's claim is enqueued BEFORE the batch graph carrying the readback,
so the claim is complete at delivery -- **strictly safer than the existing lean
shape, not merely equivalent.**

    passes/tick, peak window (30,994 chunks / 224 ticks), measured 1,203
      after fusion fix       ~186
      after band admission    ~48

What genuinely cannot convert, with arithmetic: 3 passes + 1 readback copy on a
region shape the record cannot describe (`kColumnsPerRecord` static_asserted at
1,024 = 32x32), ending in a CPU readback. Band is 6.6% of the flight:

    passes/tick = 11 + 0.066 x chunksPerTick x 4

which reaches the ~500/tick cliff only at **~1,850 chunks/tick = ~111,000
chunks/s at 60 fps -- 2.2x past the goal.** **This is NOT the same claim as
"flat", and the agent explicitly declined to write it down as one.** The term is
still linear; its coefficient is now small enough not to bind first.

### Rung 5: the Write triple's Y carry, 442 -> 1,023 records/flush

`{148, Take, 1}` instead of `{148 x Take, 1, 1}`. X stays a constant 148; the
binding stage becomes whichever still rides X with the most groups/record --
Classify and Pack at 64 -- so **1,023 records = ~61,000 chunks/s**, above the goal.

Safety rests on ONE host constant with TWO consumers:
`FVoxelGpuWorklist::kWriteRecordInY` fills the args kernel's `RecordInY` table AND
is the `VXC_WORKLIST_WRITE_RECORD_IN_Y` define the claim kernels `#error` on.
That lock is load-bearing because **the failure is otherwise silent**: a kernel
reading its record from `Gid.y` against a 1D triple sees `Gid.y == 0` for every
group, writes record 0's words 148xTake times, and leaves every other chunk's pool
words unwritten -- **holes, no error, throughput unchanged.**

checkable without a build.** If the Y dword were ignored the symptom is the silent

`-VoxelGpuWorklistVerifyClaim=1` arm on the first leg** -- its word compare is

`kRecordInY` is a POSITIONAL table with one nonzero entry; inserting a stage above

two silent failures from one edit. Pinned by assert, not by the type system.
