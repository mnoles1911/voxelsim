# The 50,000 chunks/s budget — what every per-chunk cost is allowed to be

## The arithmetic

Cold start must load **164,733 chunks**. At 50,000/s that is **3.3 s**, which is
the owner's "a few seconds". Today we measure **7,023/s and 23.5 s**.

**We need 7.1x.**

The game thread gets **5,000 ms per 5-second window**. At 50,000/s a window
carries **250,000 chunks**. So the TOTAL per-chunk game-thread budget is:

        5,000 ms / 250,000 chunks = 0.020 ms/chunk   (20 microseconds)

and that is the budget for EVERYTHING on the game thread combined, at 100%
occupancy. A sane target leaves room for the rest of the game:

        BUDGET: 0.008 ms/chunk total game thread  (40% occupancy)

## Where we actually are (measured 2026-08-23, `ahead-on` / `gp-ctl2`)

| stage | per chunk now | per-window at 50k/s | verdict |
|---|---|---|---|
| **apply** | 0.054 ms | **13,500 ms** | **2.7x OVER the whole window** |
| **submit** (post-cap) | 0.005-0.018 ms | 1,250-4,500 ms | **at or over budget alone** |
| submit (pre-cap, contended) | 0.144 ms | 36,000 ms | fixed by `-VoxelDispatchAheadCap` |
| recompute | ~250 ms/window | scales with SPAN, not rate | grows as Span^2 with 8-10 km rings |

**Two blockers, both arithmetic, neither yet solved:**

1. **Apply must get ~10x cheaper.** At 0.054 ms/chunk it alone needs 13,500 ms of
   a 5,000 ms window. The amplifier-column fix (`-VoxelApplyFast`) removes
   ~200-350 ms/window, which is real but is NOT this. Target: **<= 0.005 ms/chunk.**
2. **Submit must get ~5x cheaper.** 0.005-0.018 ms/chunk x 250,000 = 1,250-4,500 ms.
   Target: **<= 0.002 ms/chunk.**

## The property that actually decides it

Per-chunk cost is the wrong thing to optimise past a point — the thing that makes
50k reachable is work that is **FLAT IN N**: fixed per tick regardless of how many
chunks. The worklist proved the shape is available (per-chunk GPU submissions
5 -> 0, spine constant 11/tick). Anything still paid per chunk on the game thread
is a term in the 0.020 ms budget above; anything moved to per-tick is free.

**Ask of any proposed fix: does this reduce the constant, or does it remove the
term?** Removing the term is worth 10 of reducing the constant.

## What is NOT the blocker (measured, do not re-litigate)

- **The GPU.** Peak observed 14,632/s vs the CPU control's 10,291/s, and GPU
  compute sits ~1-2% utilised. Silicon was never the constraint.
- **The in-flight cap** (`cap=288` = `JobsInFlightPerCore` 8 x 36 cores). It reads
  like the ceiling — `exitCap` dominated `passes` — but results were backing up
  90,000 deep behind a starved drain. Raising it makes things WORSE. Check
  `drained` before believing any cap reading.
- **The manager tick.** `gpuMgrTickMs` is 12-47 ms against a 1,445 ms loop, 1-3%.
- **The fine-tile gate.** `rejFine = 0` in every window of every leg.
- **Render-thread backpressure.** `enqDisp/enqPoll ~ 0`.

## Standing traps that have cost retracted findings
- `grep | tail -1` lands on the post-flight linger window and reads all zeros.
  Four retractions. Use `tools/leg-summary.sh`; confirm `dispatched>0`.
- A counter reading a clean zero on the marcher path is usually an instrument
  outside the path, not an absence of cost. Twelve found this session.
- A value OBSERVED is not a limit IMPOSED. Read the constant, not the symptom.

## THE BIGGER FINDING: THE GAME THREAD IS ONLY 25% BUSY

    Voxel tick budget (5s window): ticks=103 tickMs=1304.0 (26.08% of wall)
    Voxel tick budget (5s window): ticks=107 tickMs=1233.3 (24.67% of wall)
    Voxel tick budget (5s window): ticks= 94 tickMs=1217.7 (24.35% of wall)

At steady state the streaming subsystem occupies **24-26% of wall**, and
`dispatched ~= drained ~= 15,000 per 5 s window` — about **3,000 chunks/s**.

**So the game thread is NOT the current limit.** If it were, occupancy would sit
near 100%. There is roughly **4x of unused game-thread headroom** and throughput
is not taking it.

The pipeline runs ~20 ticks/s (94-107 ticks per 5 s) applying ~150 chunks/tick.
50,000/s at 20 Hz needs **2,500 chunks applied per tick**. Something bounds
per-tick work far below what the thread could absorb. Candidates, none yet
tested: `-VoxelDispatchAheadCap` itself is binding by design
(`backlog ~= 3,964-4,620`, `exitBacklog=70-96`/window), per-tick drain/harvest
quotas, or the tick rate itself.

**This reorders the work.** Halving per-chunk cost buys nothing while a per-tick
quota caps throughput at 25% occupancy. **Find and raise the per-tick bound
first, THEN spend the per-chunk budget.** Expect the cap that binds to be sized
for a system that no longer exists — that has been true of every ceiling found
this session (promotion quota 4/tick, harvest cap 8, admission cap for a 250/s
drain, speculative lead for 20 m/s, band request per-chunk instead of
per-footprint).
