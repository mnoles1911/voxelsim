# Staged environment render-resource readiness

Staged restoration now separates CPU geometry/component preparation from render-command acknowledgment. After uploading sections, `AdvanceStagedObjectRestore` applies final LOD visibility without a bulk section traversal, processes pending render updates for one actor root, LOD root, or section per call, and inserts an Unreal 5.8 `FRenderCommandFence` at `RHIThread` depth. Later calls poll completion; they never call `Wait`, `FlushRenderingCommands`, or spin on the game thread.

Explicitly processing each component's deferred updates matters: procedural mesh creation and visibility changes can otherwise leave render-state creation pending until end of frame, beyond an immediately inserted fence. Completion is reported only after the preceding commands reach the fence's acknowledgment point. `PublishStagedObjectRestore` remains unavailable until then. The actor stays hidden and collision-disabled throughout preparation.

Cancellation retains the existing request identity and cancellation checks. An obsolete worker cannot publish into a replacement request; cancelling after fence insertion destroys staged components without waiting. The fence stores Unreal task events whose queued callbacks do not borrow the actor or staged job. The ordinary manager/controller must continue advancing the current request.

This is render-command/resource-submission readiness. It does not establish GPU execution completion, successful pixel presentation, or a shared terrain-index/actor visibility boundary. Actor publication may enqueue subsequent visibility updates. An atomic production handoff still needs coordination with terrain page reservation, upload ordering, registry binding, and one rendered-frame switch.
