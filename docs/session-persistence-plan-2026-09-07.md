# Session saving and loading: implementation plan

Research date: 2026-09-07. Planning only; no runtime changes.

Execution update: transactional storage is implemented and tested; water/basin/clock runtime capture and restoration are now connected, with river-graph and configuration compatibility limits documented separately. See [checkpoint storage notes](checkpoint-storage-2026-09-07.md) for delivered scope, verification and remaining work. The research assessment below records the pre-implementation baseline.

## Recommendation and scope

Extend the existing serializers behind one authoritative session checkpoint coordinator. A checkpoint must restore terrain, water/hydrology, persistent objects, all player records, and simulation time from the same logical instant. Single-player, listen server and dedicated server use the same implementation; joining clients receive authoritative state and never load local world saves.

Start with complete, immutable checkpoint generations and a short consistent capture barrier. Optimize capture and regional storage after correctness is established. Do not build a second terrain serializer or attempt to serialize UWorld wholesale.

This assessment covers the **current working tree**, including modified and untracked persistence/object code. It does not assert that those changes are merged, compiled or production-validated. The tree contains substantial unrelated work; implementation should re-check the baseline before editing. No AGENTS.md was found by a hidden-file repository search or in the checked ancestor directories through C:\. Repository guidance came from [README](../README.md), the [implementation plan](voxel-earth-implementation-plan.md), [backlog](backlog.md), and the domain documents below. No engine sessions or tests were run for this document.

Locked requirements from the implementation plan: 2–16 co-op players, server authority, offline single-player, deterministic terrain from canonical source data plus edits, budgeted expensive work, and **no offline catch-up simulation**. The older plan's water description is superseded by [water architecture](water-architecture.md): scalar hydrology is authoritative for flowing water, GPU PBF is reconstructible presentation, and existing CA water remains relevant for pours/cave floods. [ADR-0005](adr/0005-water-persistence.md) already authorizes persistence of irreducible CA fill and mobilization together. [ADR-0010](adr/0010-two-lattice-jurisdictions.md) and [crafting design](crafting-system-design-guide.md) require independent entity pitch and stable content IDs; the latter is a proposal, not an implemented recipe engine.

## Ownership and snapshot contract

Introduce a proposed `UVoxelSessionPersistenceSubsystem` scoped to UWorld, plus a small game-instance-scoped launch descriptor only if world travel needs it. Replace `GActiveSlug` with `{WorldId, SlotId, GenerationId, SessionEpoch, LastSuccessfulCheckpointTick}`. Keep the save library as catalog/UI facade. A directory slug is a label, not identity; identical seeds can have different world histories.

| Persisted domain | Authority and capture responsibility | Reconstruction |
|---|---|---|
| Base identity | World subsystem: seed, generation/bake/provider versions, canonical tile hashes, material/content manifest identity, lattice pitches | Resolve pinned source data before constructing amplifier. Missing content is a dependency error, not a new seed-generated substitute. Untouched bricks/chunks remain procedural. |
| Terrain/craft | Core world owns edit overlay/logs and craft promotion/ownership records | Replay terrain, then craft; rebuild edited-chunk admission, dirty LODs, collision and navigation. Never restore GPU slots, meshes or chunk residency as authority. |
| Water | Water subsystem owns CA fill plus mobilization, basin deltas, routing state and relevant tick phase | Restore after terrain. Rebuild caches/PBF presentation from scalar truth; preserve total authoritative volume and avoid duplicate handoff. |
| Persistent objects | Registry owns IDs, revisions, geometry, dynamic state, relationships and tombstones | Import records dormant; resolve references, then stream actors. Retained objects remain retained; cleanup uses remaining gameplay time. |
| Players | Server player-record store keyed by persistent player ID; controller/pawn are runtime views | Restore inventory/equipment and pawn state once, then permit interaction. Offline players remain in the store and participate in checkpoints. |
| Simulation | Owning subsystem adapters: clock, RNG streams, agents, pending durable jobs/timers | Restore clocks before ticking; rebuild paths/caches. Explicitly finish a mutation at the barrier or persist its continuation; never capture half a fracture or half an item transfer. |

At a documented game-thread point after authoritative gameplay and physics results are applied, fence new mutations for capture. Assign checkpoint tick T and each stream's last committed sequence/revision. Capture every domain from that boundary, including all connected and offline players. Fence/finish asynchronous mutations whose results belong before T; callbacks completing afterward carry epoch/revision tags and belong to the next state. Rendering jobs need not all finish if they cannot mutate authority.

Pass only immutable DTOs/byte buffers to the save worker. Initially allow a measured short capture pause, with explicit instrumentation and limits; do not assume sequential calls at arbitrary tick phases are sufficient. Later use immutable/paged core state or copy-on-write to move serialization and compaction to workers. Multi-frame copying of live mutable state without version pinning is invalid. Water's volume normalization is part of capture, before final water bytes and associated state are frozen.

Item pickup/throw/craft transfers and terrain-to-object detachment must be indivisible at T: one item/object ownership location and one material outcome. Save at a transaction boundary or persist a resumable transaction with a unique operation ID. Cosmetic particles, camera settings, UI, network channels and presentation caches are not checkpoint authority.

## Proposed schema, migration and storage

Use `Saved/SaveGames/<slot-id>/generations/<generation-id>/manifest.json` with immutable payloads and a small `current` commit record. Display name is editable metadata. Payloads may initially wrap existing formats:

```text
manifest: schema version, world/slot/generation IDs, parent generation,
          checkpoint tick, simulation time, UTC save timestamp, play duration,
          base-world/content identities, payload versions/sizes/hashes,
          required domains, stream cursors, player/object counts
terrain.vxlog       craft.vxlog (when enabled)
water.vxwater       hydro.vxhydro
objects.bin        players.bin       simulation.bin
```

Use explicit units/coordinate conventions, stable IDs instead of pointers or actor names, defined integer/float encodings, validated lengths and finite transforms. Record origin information if transforms are relative to a rebased origin. Encode full-width IDs/seeds as strings in JSON. Separate container version, actual payload format versions, and procedural/content compatibility. A schema migration cannot make edits compatible with a changed base terrain automatically.

Implement bounded pure readers and migrations to current DTOs, followed by semantic validation. Import legacy metadata v0/v1, edit logs supported by their reader, detached formats v1–v4, and seed-based water/hydro through a **copy into a new generation**, preserving originals. A legacy named save cannot prove that today's seed-water file matches its terrain: report this ambiguity and require a defined import choice; do not silently claim faithful restoration. Unknown required versions/content block load; unknown optional data must be preserved or explicitly marked unsupported, never silently discarded on resave. Missing player fields receive documented legacy defaults only.

Commit sequence:

1. Acquire a per-slot process lock and reserve a unique generation. Enforce authority/session readiness, safe resolved paths, disk/memory limits and save-guard status.
2. Write immutable payloads to that generation on the same volume; validate lengths/checksums and flush using a platform storage abstraction.
3. Write/flush the manifest listing **every** required payload, including player metadata. No required file is inferred from its absence.
4. Publish `current` using an audited platform atomic replacement primitive; establish and test durability/flush semantics on target Windows storage. Keep a validated prior commit record. File rename alone is not a proven power-loss guarantee.
5. Only then report success, update recency/active generation, and prune eligible older autosaves/orphans. Never overwrite a payload reachable from a committed generation.

Recovery validates the current commit plus complete generation; fall back only to a complete validated previous committed generation, with a visible recovery result. Ignore incomplete staging directories; never mix newest terrain with older water. Full disk, access denial, corrupt compression, missing geometry, process kill and failed rename must leave the prior checkpoint readable. Garbage collection respects manifests, in-flight snapshots and readers; initially retain whole generations instead of complex shared-blob reclamation. Content-addressed geometry and regional manifests are a later optimization. Checksums detect damage, not authenticated content.

## Load and multiplayer lifecycle

Proposed states: `Menu/Idle -> Validating -> Constructing -> Restoring -> Ready -> Capturing -> Ready`, with background writing independent of gameplay after capture, plus `Stopping` and explicit `Failed` states. Admission to writes/interactions depends on state, not merely non-null Impl.

Load order:

1. Resolve one committed generation, validate all required payloads/dependencies off-thread, run migrations into staged DTOs. Keep the prior live session or menu intact on failure.
2. Stop input/joins and authoritative mutation for a world switch; drain save jobs, cancel/tag old restore/network work, and dispose of the old registry with `Forget`. Start a fresh session epoch.
3. Construct world generation from the selected save identity, removing the current per-run-seed limitation. Reuse a controlled world recreation/travel path or extract construction/reset explicitly; do not mutate an already-built amplifier's seed.
4. Replay terrain then craft, rebuild edit-derived admission; restore water/hydro, simulation clock/RNG and persistent registry/agent records. Resolve ownership and attachment IDs in a second pass, rejecting dangling required references.
5. Stream safe collision and nearby objects at player spawn locations; restore players without default inventory seeding. A blocked/missing ground location uses a documented safe-spawn fallback while preserving original saved coordinates for diagnosis. Resume velocities only after collision/physics is ready.
6. Publish Ready only after required state installation succeeds. Cosmetic loading-screen timeouts must not bypass this gate. Enable simulation/network baseline and player interaction; clear staging on failure without writing it back.

Server identity/rejoin proposal: map a verified connection principal to a durable PlayerId in the world record store. Offline single-player gets a persistent local profile ID; online provider selection remains open. Neither display names, transient controller indices, IP addresses nor client-supplied GUID assertions establish identity. Preserve the host's player ID when opening the same world in single-player/listen-server mode. Moving to an unrelated server/account requires an explicit mapping policy.

Add login/logout hooks in GameMode and a PlayerState/view adapter. Hydrate the server record before pawn possession or inventory initialization; mark initialized even for an empty inventory. Make inventory mutation server-authoritative and replicate it to its owner; validate use/pickup/throw/craft intents. On logout copy final state before controller destruction, retain it offline, and request a checkpoint. Reject or explicitly transfer duplicate simultaneous logins; never clone inventory. An uncommitted disconnect may roll back to the last completed checkpoint after a crash; zero-loss disconnect guarantees would require a transaction journal and are outside initial checkpoint semantics.

Use a shared join envelope `{WorldId, SessionEpoch, baselineTick, domainCursors, contentIdentity}`. Stage terrain/craft/water/object baselines, buffer ordered post-baseline deltas per domain, apply them once, acknowledge installation, then enable interaction. Extend the existing object epoch checks to terrain and water; discard old-epoch callbacks and prediction on load/travel. Bound transfer memory, pace chunks, time out/retry/resnapshot under backlog pressure. Reliable RPC ordering across different actors is not assumed. Clients restore only their server-approved player record; server saves include every player, not `GetFirstPlayerController()`.

Only host/admin can request server save/load/rollback; ordinary clients can disconnect without saving an authoritative world locally. Dedicated servers require no pawn for save admission. Server rollback disconnects or rebaselines all clients under a new epoch. Host migration/cloud sync are separate future features.

Autosave proposal for P5: configurable five-minute gameplay interval while dirty, five retained autosave generations **per world**, named/manual saves never automatically pruned. Use last successful commit for staleness; no dependence on unrelated world's newest save. Coalesce periodic requests while busy; queue one manual save with clear status rather than silently rejecting it. A final save starts before actor teardown, with bounded waiting and explicit failure handling; Deinitialize is cleanup/drain, not the only chance to capture player state. Dedicated-server last-player exit does not itself shut down the world unless the configured server policy says so. No-offline-catch-up is locked; whether an online empty server pauses remains a product choice.

## Validation plan

Reuse [test_editlog.cpp](../voxel-core/tests/test_editlog.cpp), [test_craftpersist.cpp](../voxel-core/tests/test_craftpersist.cpp), existing water/core tests, `Voxel.Objects.Snapshot`/`Integrated` in [VoxelObjectPersistenceTests.cpp](../ue-project/Source/VoxelEarth/VoxelObjectPersistenceTests.cpp), and the registry/geometry/network assembly automation suites. Extend [verify-async-saves.py](../tools/verify-async-saves.py), [verify-detached-persistence.py](../tools/verify-detached-persistence.py), [verify-object-persistence.ps1](../tools/verify-object-persistence.ps1) and [verify-detached-network.ps1](../tools/verify-detached-network.ps1). Existing small object fixtures are not evidence of full multiplayer persistence; [networking notes](detached-object-networking.md) explicitly leave real fracture chains, packet loss and large transfers for validation.

Required new scenarios:

- Semantic round trip across a fresh process: terrain/craft edits at negative and large coordinates, drained cave, changed basin, chopped tree/live and dormant fragments, tombstone, player inventory, active timers and clock. Compare authoritative state/digests, not rendered frames or raw serializer ordering; separately inspect spawn/physics behavior in UE.
- Cross-domain transaction fixture: capture during pickup, throw, fracture and water handoff; assert no item duplication, lost material or double-counted water, and a single checkpoint tick/cursor set.
- Crash matrix: terminate after each payload and publication stage, including object-only save, full disk, failed rename, missing file, truncated data and corrupt current pointer. Recover one complete committed generation and preserve originals.
- Migration corpus: legacy metadata/log/sidecar formats, unknown future versions, provider mismatch, unknown required item IDs, malformed counts and compression bombs. Reject safely before replacing the live world; repeat migration produces equivalent state and never edits source fixtures.
- Multiplayer process matrix: standalone, listen host plus two clients, dedicated plus two clients; restart, late join, disconnect/rejoin, two identities, duplicate login, ordinary-client save denial, packet loss/reordering, joining while baseline changes, and rollback epoch changes. Then extend concurrency to the 16-player target.
- Lifetime matrix: two PIE worlds in one process, repeated load A/load B, menu exit, quit during active save/restore, last player leaving, and missing player pawn. No cross-world slug/job/registry leakage or callbacks into destroyed worlds.
- Long-world budget fixture: 100k terrain edits and enough object/tombstone records to cross the existing 4,096 cap; measure capture p50/p95/max, worker latency, peak memory, compressed bytes, restore time and join backlog. Initial proposed target: capture p95 <=5 ms and max <=16 ms on the agreed reference machine; these are targets to validate, not measured capability. Refuse oversize saves clearly until regional support removes the cap.

## Decisions and risks to resolve

1. **Identity provider and portability:** choose authenticated online identity and local profile storage; decide account migration and host-to-dedicated mapping. Ownership GUID already exists on objects but does not establish account identity.
2. **Enabled entity completeness:** decide durable semantics for boats/gliders, asset bodies, thrown items/explosives, agents and pending collapse/fracture. Default recommendation: persist gameplay-affecting state or finish its transaction at capture, omit cosmetics. New crafting stations/progression need adapters when implemented, not invented current fields.
3. **Compatibility/content retention:** pin canonical terrain tiles, asset banks and material/item IDs. Worldgen mismatches need preserved old generators/data or an explicit lossy world migration decision. Merely incrementing a schema cannot solve this.
4. **Legacy water ambiguity:** an old named terrain save has no matching water checkpoint identifier. Offer documented import choices; do not merge it automatically with the newest seed-water data.
5. **Save policy:** proposed five-minute/five-generation defaults, manual overwrite versus save-as branch, offline player body behavior, empty-server pause and allowable crash-loss window need product agreement. Persistent identity should survive a world branch; runtime session epoch must change on rollback.
6. **Physics fidelity:** save transforms/velocities/gameplay hinge state, rebuild Chaos internals. Exact bit-identical solver continuation is not promised; acceptance is stable reconstruction without penetration/explosion or gameplay loss. Active water presentation likewise may settle visually after load while authoritative volume remains fixed.
7. **Performance and durability:** existing game-thread terrain compaction, actor scans, geometry mutation caching and huge actor reconstruction can hitch. Use measurements before paging/COW redesign. Windows storage flush/replace guarantees and cross-process locking require implementation-level validation.

The first useful implementation milestone is P1 plus a thin P2 world checkpoint containing terrain, objects, water/hydrology and clock. It is an explicit development milestone; full session persistence is not complete until player authority, identity/rejoin, required entity coverage and the recovery tests also pass.
