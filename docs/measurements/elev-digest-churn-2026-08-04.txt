THE `ELEV_DATA` DIGEST CHURN DOES NOT EXIST. THE RE-DOWNLOAD DOES.
==================================================================
2026-08-04. Measured on this workstation against the tiles already in
D:/voxelsim/tile-cache. No tile in the world was modified by any of it.

STATUS -- READ THIS FIRST
-------------------------
The backlog item this investigation was opened on
(docs/water-waves-plan-2026-08-04.md backlog #2, restated in
docs/water-handover-2026-08-04.md section 1) says:

    "A water-only re-bake leaves the elevation plane bit-identical but changes
     the tile's identity -- 696 of 603,979,776 control points, 1 mm each --
     because no flow superblock is retained under a fine namespace."

Every clause of that is false, and the three of them are false for three
different reasons:

  * 696 is 0. Re-measured on the same nine tile pairs, through the codec's
    own decoder: ZERO of 603,979,776 elevation control points differ.
  * "1 mm each" is a unit error of 100x. `quant == 1` is the CODE for
    `QUANT_100MM`, whose LSB is 100 mm (`tile_codec.py:125-127`). One LSB is
    one voxel edge (`kVoxelSizeMm`), not a millimetre. Had the 696 been real
    it would have been 69.6 m of moved ground, not 0.7 m.
  * The superblock retention story has no difference to explain. `acc` and
    `filled` -- the two ground-bearing halves of a superblock -- are
    BYTE-IDENTICAL across four independent rebuilds of the pyramid.

What IS real is the cost, and it is much larger than the item claims. A
water-only re-bake changes 0.15-0.62% of a tile's bytes and forces the client
to re-fetch 100% of them. That is caused by `fine_provider_id`, which is in
the client's on-disk path AND in its LRU cache key, hashing the PRODUCT half
of the bake fingerprint. It has nothing to do with determinism.

WHY THE ORIGINAL MEASUREMENT WENT WRONG
---------------------------------------
Almost certainly the bv9-vs-bv10 pair, which is the only pair with 9 tiles.
Those two namespaces do not differ numerically -- measurement 1 -- but their
`ELEV_DATA` bytes differ completely, because bv9 was written CODEC_ZSTD and
bv10 CODEC_RAW. 47.6 MB against 210.7 MB on the same tile.

That trap is already written down, in `pregen._resolve_codec`'s own docstring:

    "CODEC IS NOT PART OF TILE IDENTITY. ... a RAW tile and a ZSTD tile of the
     same coordinates share a `fine_provider_id` and decode to identical
     planes. ... It also means 'same id implies same bytes' is false across a
     codec change, WHICH MATTERS TO ANYTHING THAT TREATS THE ID AS AN ETAG."

The CLI default flipped raw -> zstd on 2026-08-03, between the bv10 bake
(22:12) and the bv12 one. So the nine-tile pair straddles the flip. A digest
comparison across it reads 100% changed and means nothing about the ground.
The 696 itself is not reproducible from the shipped tiles at all; the standing
warning about hand-rolled quantisers missing the section 2 prefilter is the
likeliest second half of it.

THE REAL PROBLEM, RESTATED FROM MEASUREMENT
-------------------------------------------
The client finds a fine tile at

    <root>/<fine_provider_id>/<seed:016x>/s16/<x>_<y>.vxtl

built by `vxc::formatFineTileCacheKey(ProviderId_, Seed_, x, y)`
(voxel-core/src/tilestreaming.cpp:125), which is the SAME string used as the
LRU cache key (VoxelFineTileStreamer.cpp:164-173). `fine_provider_id` is
`fine_id_for(provider_id)` = provider id + the bake fingerprint, and that
fingerprint hashes BOTH halves:

    _tile_format_fingerprint() = sha256({"bake": bake_identity_payload(),
                                         "product": product_identity_payload()})
                                          (providers/diffusion.py:846-854)

So a PRODUCT-only bump moves the path and the cache key, and the client
re-fetches every byte of every tile whether or not one changed. Byte-stable
elevation buys nothing against that, and it is already byte-stable.

One further fact worth having before anyone prices a fetch optimisation:
there is no fine-tier transport. `terrain_service/app.py` has exactly two
routes, `/healthz` and `/tile`, and `/tile` serves the COARSE tier only, with
no ETag and no conditional request. Fine tiles reach the client as files in a
directory named by `-VoxelFineTileDir` + `-VoxelFineTileProviderId`. "Every
client re-downloads every tile" describes a distribution system that has not
been built yet.

WHAT THE THREE CANDIDATE FIXES ARE WORTH
----------------------------------------
1. MAKE THE RE-BAKE BYTE-DETERMINISTIC. Already true. Measurements 1, 2, 3
   and 4. Nothing to build.

2. RETAIN THE FLOW SUPERBLOCK ACROSS A WATER-ONLY RE-BAKE. Measurement 5: it
   cannot change a byte, because the rebuilt pyramid already reproduces
   exactly. It is a CPU saving of about 1.7 s against a 313.5 s tile, i.e.
   0.5%, and it is worth building only if someone wants that 0.5%. It is not
   a fix for this.

   (Note that within one namespace superblocks ARE already retained and
   reused: the re-bake in measurement 4 loaded all five from cache in 1.7 s
   and re-verified their fingerprints.)

3. STOP THE IDENTITY DEPENDING ON BYTES THAT DID NOT CHANGE. The only live
   option, but NOT in the form the backlog item imagines. There is no need
   for a coarser quantisation tolerance or a fuzzy content hash: the bytes are
   already identical, exactly, so an exact per-section or per-block content
   address captures the entire saving. Measurement 3 says that saving is
   99.4-99.85% of the transfer.

   This is where the design decision the owner has to make actually sits, and
   it is stated in the section below rather than chosen here.

THE DECISION, AND WHY IT IS NOT MINE TO MAKE
--------------------------------------------
Two ways to collect the 99.4-99.85%, with different risks:

  A. PER-SECTION / PER-BLOCK CONTENT ADDRESSING (task #52's shape). Leave
     `fine_provider_id` exactly as it is -- one world, one namespace, two
     different bakes always distinguishable -- and let a client ask for the
     sections or blocks it does not already hold. Nothing about what a world
     IS changes; the only new thing is that bytes are named by their content
     as well as by their path. `.vxtl` v2 already frames every block
     independently and the index already carries
     (offset, comp_len, mode, const_cp, resid_bits), so the format needs no
     change. Cost is entirely in the transport, which does not exist yet.

  B. SPLIT THE NAMESPACE: address the terrain-bearing sections under
     `bake_fingerprint()` (the terrain half) and the product sections under
     `product_fingerprint()`. Cheaper for the client -- the elevation path
     simply stops moving -- but it puts two different bakes' tiles at one
     path, which is the collision the content-addressing rule exists to
     forbid. It would need the per-section identity checked explicitly rather
     than implied by the directory, and getting that wrong is exactly the
     "one namespace containing two different planets" failure the
     world-identity work spent a day on.

A is safe and needs a transport first. B is cheap and moves a load-bearing
guarantee. Which is right depends on whether fine tiles are ever going to be
served over a wire at all, and that is the owner's call, not a measurement.

Recommendation, offered and not acted on: do NOTHING until there is a fetch
to optimise. Today the re-download is a directory name changing on one
workstation. The measurement above will still be true when a transport
exists, and it says the whole of the elevation and flow planes will be
reusable when it does.

WHAT WAS RULED OUT ALONG THE WAY
--------------------------------
* NUMBA PARFOR FUSION IN `thermal._step`. The module docstring's safety
  argument ("two passes ... no cell writes to a neighbour") holds only if the
  two `prange` loops are not fused, and nothing in the repo disables fusion.
  Checked rather than assumed, with NUMBA_DEBUG_ARRAY_OPT_STATS=1 over a cold
  cache: "After fusion, function _step has 2 parallel for-loop(s) #{0, 1}."
  Not fused, so the barrier between the passes stands and there is no race.
  `thermal.relax` on the production field path also returned one digest over
  five repeats at 2048^2 x 48 iterations.

* THREAD COUNT / FLOAT NON-ASSOCIATIVITY generally. Nothing in the bake sets
  NUMBA_NUM_THREADS; it is 12 here. There is no float atomic add and no
  parallel reduction anywhere in the bake -- `accumulate_mfd`,
  `accumulate_d8` and `fill_depressions` are all explicitly sequential. This
  was never going to be the cause once measurement 5 came back identical.

LATENT, FOUND WHILE LOOKING, NOT FIXED HERE
-------------------------------------------
`incise._profile_levels` reasons explicitly against stable-sort tie-breaking
("a float32 tie breaks that: argsort(kind='stable') then orders the pair by
index, so a donor can be visited BEFORE its receiver") and its own fallback
uses `kind="stable"` (incise.py:781). In production the order is handed in
from `accumulate_mfd(return_order=True)`, which uses the DEFAULT sort kind
(flow.py:575, and flow.py:647 for `accumulate_d8`). Deterministic on one
machine and one NumPy, so it is not this bug; it is a portability edge, and
NumPy 2.x changed the 32-bit sort to a CPU-feature-dispatched implementation.
Worth an aligned `kind="stable"` if anyone is in there anyway.
