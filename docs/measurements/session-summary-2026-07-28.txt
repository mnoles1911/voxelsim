WHAT SHIPPED
============================================================================

1. T4-1 SPECULATIVE GENERATION (Wave S4 closed)
   Median transient holes during flight ~822 -> ~57, a 93% reduction,
   replicated across a 10-leg alternated sweep. No throughput cost, no memory
   cost, and after the batch-scope fix no game-thread cost either.
   Detail: docs/measurements/t41-first-result-2026-07-28.txt

   The lead time is NOT a tuning knob: 1 s captures the whole effect and 8 s is
   no better. Default recommended at VelocityLeadSec 2.0; still gated OFF
   pending the owner's call.

2. DRAW PATH: 32.7 -> 65.7 fps AT 2K
   GPUCullMergeGap 4096 -> 64 and GPUCullMaxRanges 1024 -> 16384. Over-draw
   3.4x -> 1.001x (drawn 33.1M -> 9.72M against 9.71M visible). Hitch frames
   3,747 -> ~11.
   Detail: docs/measurements/drawpath-2k-2026-07-28.txt

   RESOLUTION IS FREE: baseline is 30.61 ms at 900p and 30.59 ms at 2K, 2.56x
   the pixels for zero cost. The renderer is geometry/submission-bound. Re-check
   this after any change; the moment something becomes pixel-bound the 900p
   sweeps stop transferring.

   THE TWO KNOBS ARE INSEPARABLE. Swept alone, MaxRanges 16384 measured WORSE
   than 4096 and would have been rejected. A coarse gap merges away the ranges a
   large budget exists to keep; a fine gap produces them and the budget keeps
   them. One-at-a-time sweeps measure each knob at the other's wrong value.

3. POOL CAPACITY 64M -> 80M quads, table 81,920 -> 98,304
   Sized from a measured plateau (highWater 59.24M on a 330 s traverse), not
   from the plan's 104M guess -- that was justified by a large speculative
   parked population which does not exist (peak 172 chunks against a 4,000 cap).
   Buys CONTIGUITY: largest free run 6.8M -> 22.4M.

4. SMALLER FIXES
   - Manager two-queue priority so speculation uses idle GPU without delaying
     demand (voxel.GPU.MeshSpeculativeBatchCap).
   - Pool batch scope widened over GpuMeshJobs->Tick(): speculative parks were
     republishing the whole chunk table individually, 97% of T4-1's cost.
   - Speculative results now store their D6 band, so the buried skip can fire on
     virgin terrain at all (bandSkipped 0 -> 51/window).
   - Run rebuilds gated on bRunsDirty rather than bTableDirty.
   - Park census hit rate no longer divides all adoptions by demand-only parks
     (it printed "hit 102%").
   - tools/voxel-audit-leg-overlap.ps1: proves from log timestamps that no two
     legs shared the box, including legs the runner's guard never saw.

60 FPS AS A FLOOR -- p50 clears 60 at 2K; p95 (20.9 ms, ~48 fps) does not. The
  gap is the streaming tick: 5.995 ms per tick landing on ~32% of frames, of
  which the pool publication is over half (buildRuns 2.94 ms, runBounds 1.28 ms
  per push, walking ~53,800 allocations). Eliminating buildRuns ENTIRELY would
  still leave p95 around 18.3 ms, so a floor needs the streaming tick off the
  frame's critical path -- time-slicing or a worker thread. That is a design
  decision, not a tuning change.

---------------------------------------------------------------------------
WHERE THE FRAME ACTUALLY GOES (measured, replicated)
---------------------------------------------------------------------------

  render thread   13.5-13.7 ms   <- this IS the frame
  game thread      3.0-3.6 ms working, 10.1-10.7 ms WAITING
  voxel tick       0.4-0.5 ms on a typical frame
  GPU frame       16.8-18.4 ms   <- the actual bottleneck

  GPU split: meshing compute 21-28% | PrePass ~5.6 | BasePass ~5.9 (+/-1%)
             | post ~1.4 (TSR 1552x873 -> 2560x1440, so "2K" is UPSCALED)

  render-thread split: cull walk ~1.0 | range emit ~3.2 | NOT the pool ~9.5

THE TWO FACTS THAT DECIDE EVERYTHING ELSE:

1. THE GAME THREAD IS IDLE 75% OF THE FRAME. Gameplay systems -- AI, physics,
   inventory, networking -- are game-thread work and have enormous headroom.
   What is full is the render thread and the GPU, which is where VISUAL
   additions land. Every streaming optimisation in this programme landed on the
   thread that was already idle.

2. WORK REMOVED FROM A SUBSYSTEM DOES NOT RELIABLY BECOME FRAME TIME. Cutting
   game-thread publication 2.94 -> 0.055 ms: p50 unmoved. Cutting speculative
   GPU dispatches by 46%: p50 moved 0.08 ms. The GPU meshing evidently overlaps
   with rendering rather than sitting on the critical path.

---------------------------------------------------------------------------
SEVEN FALSIFIED PREDICTIONS, AND THE RULE THEY EARN
---------------------------------------------------------------------------

  1. the streaming tick causes the frame tail   removed 1/3 of it, p50/p95 flat
  2. shadow cascades re-gather the pool 4-5x    shadowGather=0
  3. the cull walk costs ~4.4 ms                measured 1.0 ms, wrong by 4x
  4. the streaming tick is "a passenger"        true on CPU, false on GPU
  5. the prepass is a removable misconfig       Nanite hands off to DBuffer;
                                                BasePass unmoved across 4 arms
  6. cutting mesh dispatches buys ~1-1.5 ms     bought 0.08 ms
  7. BaseVertexIndex can replace BaseQuad       already falsified in the .ush
                                                (caught by READING, not building)

Each had a number behind it. The rule: NO ITEM GOES ON THE PLAN WITH A PREDICTED
SAVING UNTIL AN EXPERIMENT HAS REMOVED THAT WORK AND MEASURED THE FRAME. On this
renderer the mapping from subsystem cost to frame time is not additive, and
guessing it has been wrong seven times out of seven.

---------------------------------------------------------------------------
WHAT IS LEFT, AND WHY IT IS NOT OBVIOUSLY WORTH DOING
---------------------------------------------------------------------------

Realistic ceiling from remaining items is ~12-13 ms (~80 fps), NOT 10. And both
of the largest are blocked on a question nobody has answered:

  HOW MUCH OF THE 18.4 ms GPU FRAME IS SERIAL AT ALL?

Finding 2 above showed one large GPU component (meshing, 21-28%) that is NOT on
the critical path. Occlusion culling and indirect drawing may hit the same wall.
Establish serial-vs-overlapped before building either.

100 fps needs the primitive count down -- 17.8M per pass, submitted TWICE, into a
1552x873 internal target, about 11 triangles per rendered pixel. That means
drawing distant rings (L3-L5, 53% of pool quads, 512 m to 4 km, sub-pixel voxels)
as heightfield rather than voxel geometry. AVoxelClipmapActor already exists.
That is a FEATURE, not an optimisation.

RECOMMENDATION AT SESSION END: build gameplay. The renderer holds ~65 fps at 2K
with zero holes, the game thread has 10 ms free for exactly the systems that come
next, and real content will reshape the profile anyway. The instrumentation to
watch it move is now in the tree (FrameAttribution, GPUCullTiming, DeferExec,
voxel-run-gpu-arm.ps1, voxel-audit-leg-overlap.ps1).
