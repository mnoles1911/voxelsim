--------------------------------------------------------------------------------
THE MECHANISM, AND IT COMPOUNDS
--------------------------------------------------------------------------------

  per leg                    off        on
  pool publications      118,762      7,205     16.5x fewer
  applies completed       70,106    233,477      3.3x more
  mean stale fraction         42%         0%

This is the chain S0 predicted from the queue-backlog finding, confirmed end to
end:

  publication amortised over a tick instead of per chunk
    -> per-apply cost collapses
    -> 3.3x more applies fit in the same 6 ms budget
    -> the ResultsQueue stops backing up
    -> results are applied while their records are still live
    -> the stale fraction goes 42% -> 0%
    -> none of the GPU's output is thrown away
    -> coverage converges: 14,827 holes -> 966

The stale collapse is the half that was not obvious from the design. Batching
was justified as an amortisation of a per-item cost; most of the delivered win
is that the pipeline stops discarding 42% of the work it had already paid the
GPU to do. Throughput and waste were the same problem.

--------------------------------------------------------------------------------
POOL FRAGMENTATION -- THE REVERT CONDITION, AND IT FIRED
--------------------------------------------------------------------------------

  leg          batchPublish   allocFail   allocFailQuads
  s11-off-1    0                      0                0
  s11-on-1     1                 77,290       96,933,454
  s11-on-2     1                 75,382       94,853,610

Batching refuses ~76,000 allocations per leg. Unbatched, on the same binary over
the same route, it refuses none.

IT IS FRAGMENTATION, NOT EXHAUSTION, and the pool's own early-warning counters
say so exactly. GetFreeRunCount's doc comment: "1 means unfragmented. Rising
while GetFreeQuads() stays healthy is the early warning that allocations are
about to start failing on a pool that still looks half empty." End of leg:

                         batching ON     batching OFF
    free quads            27,872,095       24,751,830
    largestRun                68,326        4,904,120
    freeRuns                  16,903            8,407
    capacityPct                 61.2             61.2
    liveChunks                28,613           21,437

Same total free, a 72x smaller largest contiguous run.

THE CHAIN. First refusal happens at liveChunks=49,349, capacityPct=98.5,
largestRun=1,941, freeRuns=6,640 -- i.e. the pool genuinely filled first. 3.3x
apply throughput drives transient residency far above the 39,020 the pool was
sized from; first-fit then refuses; the free list shatters; and refusals keep
coming after residency falls back to 28,613 and the pool reads 61% free.

49,349 live chunks ALSO crosses the 49,152 chunk-table floor, which takes
PushUpdatesToProxy's MarkRenderStateDirty branch -- and per D4-R1 that
invalidates every GPU-written range. Both ceilings were sized from the old,
slower throughput.

So S1-1 is the right change with the wrong sizing around it. It is not a
batching bug; it is batching outrunning two numbers derived from a pipeline that
could not go this fast.

Why holes still FELL (14,827 -> 966) while geometry was being refused: coverage
verify counts footprints nothing visibly covers, and at 2.2x the throughput far
more footprints get covered even with refusals. The two are not in conflict, and
neither excuses the other -- 96.9 M quads of refused allocation is missing
geometry whatever the coverage number says.

--------------------------------------------------------------------------------
WHAT IS NOT VERIFIED, AND IT IS THE DANGEROUS PART
--------------------------------------------------------------------------------

  dirtyOverlapsResolved = 0 on both batched legs.

The free-then-reallocate-within-one-frame guard (UnmarkQuadsDirty) NEVER FIRED.
Ground rule 13: a code path with no recorded executions is untested, however
green everything around it is.

Why it is nearly unreachable, from reading the tick: within one FScopedBatch the
order is DrainResults -> DrainGameThreadMesh -> DrainUnloads. GPU allocations
happen only in DrainResults (ApplyMeshResult -> AddChunkFromGpu); most frees
happen after it. So frees mostly follow allocs and cannot be re-allocated in the
same batch.

Why it is NOT unreachable: ApplyMeshResult's zero-quad branch calls
ReleaseChunkGeometry INSIDE DrainResults, freeing a range and marking it dirty,
and a later result in the same drain loop can AddChunkFromGpu. It needs the
first-fit allocator to hand back that specific run, which did not happen in four
legs.

So the guard is load-bearing for a case that did not occur. That is the worst
state to ship in: if the subtract is wrong, nothing here would have caught it,
and the failure mode is INVISIBLE TERRAIN THAT REPORTS AS LOADED.

  ACTION TAKEN: the interval algebra is covered by automation tests instead of
  by hope -- all five cases (disjoint, fully covered, keep head, keep tail, and
  the split-in-two case that is the one that silently corrupts). See
  VoxelEarth.GpuPool in VoxelGpuGeometryPoolTests.cpp. Pure interval logic, no
  GPU, so it runs in CI-shaped conditions rather than needing a leg.

Also not run: voxel.Stream.PoolClobberTest. It cannot execute from -ExecCmds --
it fires at frame 0, before the pool component exists, and logs exactly that.
The live PoolClobberSession variant (settle delay, screenshot noise-floor pair,
clobber, third shot) is the one that can run against a streamed world.

--------------------------------------------------------------------------------
WHAT THIS DOES NOT CLOSE
--------------------------------------------------------------------------------

581 chunks/s is short of the >= 900 this item targeted and well short of the
1,082 the Wave S1 close requires against the component arm. Batching removed the
per-CHUNK term; two things S0 measured are still standing:

  * BuildChunkRuns still walks an append-only Allocations array, so its cost
    tracks chunks EVER ADDED (3.72x waste by end of flight). Batching divides how
    OFTEN that walk happens, not how big it is. That is S1-2.
  * RebuildRunBounds is still a full O(live runs) rebuild per publication on the
    render thread. That is S1-4, still conditional on the post-S1-1 number.

Re-read the per-apply and pool-publish lines on these legs before starting S1-4:
the S0 census was taken at ~1,700 publications/second and the shape at 60/second
may be different.
