RETRACTED: "ONE LEG IN FOUR DID NOT FINISH". That was MY HARNESS, not the fork,
and the time series says so plainly. fork 2 was still filling when it died --
loaded went 41,968 -> 42,625 in its final two seconds, with pending RISING from
78 to 174. Nothing was stalled.

The inline PowerShell loop used for these runs breaks on the first
"jobsInFlight=0 pendingJobs=0" it sees. At t=30.3 s that was true as a TRANSIENT
LULL mid-fill (loaded=39,328 of 43,328), so the loop slept 8 s and killed the
process at t=38.4 s while the cascade was still building.

This is the SAME artefact already found and fixed once in tools/wave-f-coldfill.ps1
-- "a lull is not a finish line" -- and it came back because these runs were
driven by a fresh ad-hoc loop rather than that script. The fix exists; it was not
used. fork 3 shows what a real completion looks like: pending reaches 0 at
t=42.3 s with loaded=43,328 and the run continues to 54.5 s.

So: FOUR of four legs were fine, three measured (42.4 / 42.3 / 42.4 s) and one
void. There is no residency tail.

ONE THING THAT IS STILL REAL AND NOT RETRACTED.

A 7,395 ms SUBMIT->DELIVER OUTLIER, which is ABOVE kBlindJobMarkTimeoutSeconds
   (5.0 s). gpuLatencyTimeouts stayed 0 -- that counter only fires for a
   footprint whose band mark is outstanding, and a footprint with a cached band
   has no mark to time out -- so the backstop was not tripped, but the latency
   that would trip it now occurs. Boundary chunks are the coarse ones, and a
   level-4 dispatch covers 16x the world area of a level-0 one.

DO NOT COMPARE THESE TO THE PRE-SKIRT NUMBERS ACROSS SESSIONS. The CPU baseline
itself moved from 58.4/60.4 s to 62.4/62.5 s between the two runs, which means
the box is not in the same state -- so the honest comparison is within-session
ratio: pre-skirt fork/CPU 36.3/58.4 = 0.62, post-skirt 42.4/62.5 = 0.68. The
fork is still clearly ahead and is doing MORE work than before; the ratio moving
the way it did is what you would expect from adding the coarsest chunks, not a
sign of a defect.

--- FOLLOW-UP: the slow-delivery counter, and two clean legs -------------------

Re-run through tools/voxel-run-leg.ps1 (the safe stop condition), with the new

  slow-gpu-1  settle 40.4 s  peak 43,328  forked 33,957  max 814.6 ms  slow(>=5s)=0

Both settled genuinely -- loaded unchanged for three consecutive samples with
nothing in flight and nothing pending -- rather than on a lull. 40.4 / 42.4 s
against the same session's CPU baseline of 62.4 / 62.5 s.

So the 7,395 ms outlier did NOT recur across two further legs, and the counter
that would have caught it now exists and reads zero. That is a better position
than the earlier run, where the only evidence of health was a counter
structurally incapable of disagreeing: gpuLatencyTimeouts fires when a cold-band
MARK ages out, and a mark exists only for a footprint whose band was not already
cached. With bandCache warm at 5,088 entries, almost nothing carries a mark, so
arbitrarily slow deliveries passed it untouched.

The outlier is not explained, only unobserved since. A level-4 dispatch covers
16x the world area of a level-0 one, so the coarse chunks the skirt newly admits
are the plausible source; if it returns, slow(>=5s) is now the line that says so.
