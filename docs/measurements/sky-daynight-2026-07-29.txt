2. THE THREE DEFECTS THE LADDER FOUND
-------------------------------------
None of these would have been caught by a unit test. All are fixed.

(a) Twilight rendered PURE BLACK.
    Before:  sun -5.1 deg -> mean 0.02, 0.0% non-black
             sun -3.8 deg -> mean 0.02, 0.0% non-black  (byte-identical files)
    After:   55.17 / 98.3% and 83.47 / 96.6%
    Cause chain, verified in engine source rather than guessed:
      SetVisibility(false) -> CreateRenderState_Concurrent skips AddLight
      -> ProcessAtmosphereLightRemoval clears AtmosphereLights[0]
      -> sky pass integrates zero radiance -> black sky
      -> real-time-capture SkyLight captures that black sky as ambient.
    The obvious fix reproduces it: UpdateColorAndBrightness computes
    bValidIntensity as Intensity > 0 unless the light is in EV units, and a
    DirectionalLight is Unitless, so "set intensity to 0" hides it too.

(b) The moon lit terrain twice as orange as the sun.
    kMoonTemperatureK was 4100 K, with a comment correctly arguing for a cool
    Purkinje shift. Colour temperature runs backwards from the word "cool":
    linear RGB at 4100 K is R:B 2.48 against the sun's 5778 K at R:B 1.22.

(c) The darkest night of the year rendered BRIGHTEST.
    The exposure curve capped flat below -2 deg, so it could not distinguish a
    -14 deg midsummer midnight from a -61 deg midwinter one. USkyAtmosphere
    models scattered sunlight only, so its sky is equally dead at both, leaving
    deep night rendered by whatever the moon was doing — and the moon rides
    higher in winter.

4. THE MOVING-SUN COST  —  ANSWERED, AND IT IS FREE
---------------------------------------------------
The open risk was that docs/backlog.md section 0 measured cascades cheap
(shadowGather=0, ~1.03 gathers/frame) with a sun FROZEN SINCE SPAWN. A static
movable directional light lets the engine cache whole-scene shadows; a rotating
one busts that cache every frame. The measurement did not transfer, so it was
re-taken.

tools/voxel-sun-arms.ps1, alternating arms (F,M,F,M — never grouped), 2560x1440,
line flight, 90/120/60 s, identical spawn/seed/route/date, differing only in
-TimeScale. Leg 1 discarded for a cold shader cache (722 hitches against 347).

  arm      p50      p95      max     hitches   sun
  FROZEN   15.18    25.31    69.52     347     alt 37.55, tod 12:00
  MOVING   15.18    25.32    78.19     268     drift 29.4 deg, 12:02 -> 17:23

  p50 identical. p95 identical to 0.01 ms.

  CAVEAT THAT MUST TRAVEL WITH THIS NUMBER: measured with
  voxel.Sky.ShadowUpdateHz = 10, i.e. the light's orientation is re-asserted at
  10 Hz, not every frame. It is THAT CONFIGURATION which is free. An uncapped
  rotating light has not been measured and this result says nothing about it.

  A first attempt at this leg was VOID: it was the first run after a build, the
  editor spent ~5 minutes compiling shaders before the world existed, and the
  480 s wall fired mid-flight. Its editor then outlived the script and the
  one-editor guard correctly refused the remaining three legs rather than
  producing contended numbers. Discard the first run after any build.

  FOUR SILENT-FAILURE TRAPS FOUND WHILE AUTHORING THE MATERIAL. None was a
  compile error; every one would have shipped a wrong-looking sky:

  (a) FCollectionParameterBase::Id is protected for READ as well as write on
      UE 5.8, so the script could neither set stable guids nor verify them. An
      unresolved CollectionParameter does not fail to compile -- Compile emits a
      CONSTANT -- so a typo ships a black sky with no diagnostic. Replaced with a
      name-membership check against the MPC as read back, which is possible and
      strictly stronger: the script authors the collection, so it knows the
      complete valid set.
  (b) MaterialExpressionClamp's first input is UNNAMED. Its pin list is
      ['None','Min','Max'], so "Input" never matched. Caught only because every
      connect in these generators raises rather than warns.
  (c) The documented tuning knob did not exist. A comment said to tune "the MPC's
      own StarBrightness default (an asset edit, no regeneration)", but the
      subsystem writes that scalar every frame, so the asset default is
      overwritten before anything renders. Hence voxel.Sky.StarGain. Once C++
      drives a collection scalar, that scalar's asset default is dead as a tuning
      surface -- the same trap the star-map handedness note hit for StarRotation.
  (d) THE CLIPMAP IS BIGGER THAN EVERY DOCUMENT SAID. "The 50 km clipmap" appears
      in this plan, in create_sky_material.py's header, and in the brief that
      commissioned the dome. Measured from the geometry: the outer half-extent is
      16 x RingEdgeUU = 65.5 km at the shipped 4 km cascade, and the farthest
      drawn point is the grid CORNER at 92.7 km. The numbers predate the cascade
      moving from 1 km to 4 km; VoxelClipmapActor.h's own "~16.4 km" is stale for
      the same reason. The 2e7 UU dome clears the corner by 2.16x, and
      AVoxelClipmapActor::OuterHalfExtentUU() now derives it so the dome can check
      itself at BeginPlay and error rather than be silently occluded.

  Still not verified, and only checkable by eye: star-map U handedness (a mirrored
  celestial map still gives a sharp sky rotating at the right rate with the pole
  at the right altitude -- only the constellations are reversed), and whether any
  constant RA offset is needed. voxel.Sky.StarUDirection and
  voxel.Sky.StarRotationOffsetTurns exist for both, no rebuild required.


6. THE SKY LIGHTING THE GROUND (S1 + S2), 2026-07-29 late

The star dome could not light anything: the SkyLight's real-time capture renders
only the atmosphere, clouds, height fog and meshes whose material sets bIsSky,
and M_NightSky sets is_sky False deliberately. Fixed by adding a canonical IsSky
dome (M_SkyAtmosphereDome) that the capture CAN see, with the star branch behind
a ReflectionCapturePassSwitch so stars reach the capture and never the main view.

WHY THIS UPDATES ITSELF. The light comes from a per-frame capture of the dome
material, not from a baked cubemap. Change T_SkyStarmap, the gain, or the graph
and the ambient light on the terrain follows within a few frames with no re-bake.
The rejected alternative -- prefiltering the EXR into SH offline -- would have
needed a re-bake on every art change. The moon is deliberately the exception: its
LIGHT is a directional light scaled by illuminated fraction, and its DISC art is
kept out of the capture so it cannot light the world twice. The engine enforces
the same for the sun disc (MaterialTemplate.ush:2346-2348, "avoid double
specular").


7. COUPLING THE TWO STAR GAINS, AND A GATE THAT IS NOT READY
------------------------------------------------------------
Concern raised: the Milky Way looks very bright against a much darker ground --
is that realistic? It is, and here is the yardstick. For a Lambertian surface
under a sky of luminance L_sky the illuminance is E = pi*L_sky and the surface
reads rho*E/pi, so L_ground / L_sky == ALBEDO. Geometry, units and exposure all
cancel in the ratio.

Measured on a starlit capture (22:00 on 03-20, core high, +3 EV for visibility
which cancels), proper sRGB EOTF, clipped pixels excluded, Y = 0.2126R + 0.7152G
+ 0.0722B:

  whole visible sky   0.14342 linear
  Milky Way core      0.27833
  snowfield ground    0.11325
  snow / sky          0.790     <- snow's albedo is 0.75-0.85

So the ground receives light in correct proportion to the sky casting it. The
"bright sky, dark ground" impression is because most of the frame is water and
dark vegetation at 0.03-0.10 albedo, which are CORRECTLY 10-30x darker than the
sky. What the frame resembles is a long-exposure photograph, which is what
essentially all Milky Way imagery is; to the naked eye the band is a faint smudge
and the ground is unnavigable.

A PREMISE THAT WAS WRONG, AND THE BUG IT NEARLY CAUSED. The concern was framed as
"voxel.Sky.StarGain and voxel.Sky.StarAmbientGain are independent knobs and
nothing couples them". They are not independent. BOTH domes multiply the same MPC
scalar StarBrightness, which the subsystem writes as sunriseFade * StarGain:

  visible (create_sky_material.py:628)                StarMap * StarBrightness * fade
  capture (create_sky_atmosphere_dome_material.py:286) StarMap * StarBrightness * fade * StarAmbientGain

so StarAmbientGain is a pure RATIO with no StarGain left in it -- StarGain already
reaches the ambient term linearly. The proposed fix, deriving
StarAmbientGain = StarGain / 0.15, would have multiplied StarGain in a SECOND
time and made ambient starlight QUADRATIC in it: at StarGain 0.30 stars would look
2x brighter and light the world 4x harder. It would have been bit-identical at the
shipped defaults, so no gate would have caught it.

What was actually unenforced is that StarAmbientGain was a free artistic knob
whose correct value is a measured constant. It now defaults to a negative sentinel
meaning "derive from kStarAmbientCalibration" (1.0, measured at StarGain 0.15),
with any value >= 0 taken as an explicit override so the S2 A/B still works. The
resolved value AND whether it was derived or overridden are both logged, because
with a sentinel default echoing the cvar would print -1 for a frame that rendered
at 1.0 -- the one reading that says "starlight was off".

  Gate: explicit 1.0 vs derived, one process, same epoch and pose
    sky    mean 110.8418 vs 110.8423
    ground mean  37.7295 vs  37.7558

  PASS. Note "bit-identical" was the wrong bar and is not achievable here: per-
  pixel deltas reach 29 with 3-7% of pixels differing, because TSR resolves a
  point-star field slightly differently between two frames of identical input.
  Mean luma is the right instrument, and 0.014 against S1's 2.0 standard is a
  140x margin.

tools/sky-albedo-check.py IS NOT A GATE YET, and its header says so. Two runs at
identical pose, date, hour, exposure and resolved gain gave ratio 0.7928 (snow
mask 8.39% of frame) and 0.6446 (12.62%) -- a ~20% spread on a quantity tested
against a +/-6% band, with the mask growing by half. It is partly measuring frame
CONTENT, most likely differing terrain streaming state, so a FAIL from it does not
currently distinguish a drifted calibration from a differently-streamed run. It
needs a deterministic reference surface: a fixture-spawned quad of known albedo at
a known screen rectangle, or a fixed pixel window gated on streaming convergence.
