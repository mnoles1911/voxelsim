# Lessons from the S0/S1 waves (2026-07-27, second session of the day)

Executing `docs/speculative-generation-plan.md` Waves S0 and S1. What was
learned, separated from what was built, because the lessons outlive the code.
Companion to `docs/lessons-2026-07-27-gpu-sessions.md` from earlier the same day.

## Progress, in one block

- **The ~600 chunks/s pooled plateau is gone**: 260.9 → 797.0 chunks/s at the
  adopted 128 m / 4 km cascade, with **converged holes 15,032 → 0** — the first
  time the pooled arm has completed the world at this scale.
- **§1a confirmed then discharged.** The apply loop went from never once
  reaching an empty queue to queueEmpty-dominant, and the stale-result fraction
  from 42% to 0%.
- Shipped: batched pool publication, handle recycling, pool 44M → 64M, chunk
  table 49,152 → 81,920, unload budget 24 → 256, plus the S0 instrumentation the
  whole thing was diagnosed with.
- **The bottleneck moved into admission**, and S1 is what moved it there.

## Lessons

1. **A metric that divides by the wrong ceiling can invert a diagnosis.**
   The open P0 read "apply budget only 8.5% saturated — results are not
   ARRIVING", from `LastAppliedFrac` dividing applies by the COUNT cap while the
   loop actually breaks on a 6 ms WALL CLOCK. Measured, `queueEmpty` was 0 in
   every streaming window: results were arriving faster than they could be
   applied. The programme spent a session sweeping producer-side knobs against a
   consumer-side wall because of a denominator.

2. **Read the raw line before quoting a field — especially a field that is a
   revert condition.** `allocFail=0` was published in a measurements file and a
   PR body having never been extracted; the regex that produced the sentence
   truncated before it. The real value was 77,290 (96.9 M quads). A default was
   flipped on that claim and had to be reverted.

3. **Zero and "not measured" are different, and a log line must say which.**
   Twice: gated timings read `0.00ms` because `-ExecCmds` lost every cvar after
   the first space (`Start-Process` does not re-quote arguments containing
   spaces), and three latency stages read `0.0` because a second, cross-module
   cvar was off. Both look like "this costs nothing" — the exact opposite of the
   truth — in an otherwise healthy log. Log lines now state when their inputs
   were not measured.

4. **Never conclude from a run that was sharing the box.** Two legs overlapped
   for 86 seconds because a sweep was launched before the previous sweep's loop
   finished. Nothing errored; both wrote real logs; the numbers were contended.
   The contaminated leg produced "MaxAppliesPerFrame 192 is worse" — with a
   plausible mechanism attached — and that went into a measurements file before
   the overlap was noticed *by a human seeing two game windows on screen*. That
   is not a control. `tools/voxel-run-flight-leg.ps1` now refuses to start while
   any editor is alive. This is ground rule 1's sibling.

5. **A symptom that looks like an allocator bug can be a budget that is one
   pipeline-generation out of date.** Batching produced 16,903 free runs and a
   72× collapse in largest-free-run at equal total free — textbook first-fit
   fragmentation, and the obvious response is to build a compacting defragmenter
   (T3-6). It was residency ballooning because `MaxUnloadsPerFrame=24` was sized
   for a 260 chunks/s pipeline. One cvar took refusals 26,763 → 0 and holes
   257 → 0. **Every per-frame budget is a hidden assumption about throughput;
   any change that moves throughput must re-sweep the ones downstream of it.**

6. **Measure the thing before building the fix for it, even when the reasoning
   is airtight.** Three items died or were demoted this way: T1-3's params cache
   (the cost it targeted is 0.2% of an apply), T3-6 idle defrag (symptom, not
   cause), and S1-2's promotion (the 3.72× walk:emit ratio was real, but cost
   tracks `emit` not `walk` — `BuildChunkRuns` is dominated by `Runs.Sort`).
   Each was argued convincingly from code before a leg contradicted it.

7. **A guard that never fires is not a guard that passed.** S1-1's
   free-then-reallocate subtract did not fire once across four flight legs. The
   race is genuinely rare — tick ordering puts most frees after allocs — but it
   is reachable, and the failure mode is invisible terrain that reports as
   loaded. Ground rule 13. It is now covered by `VoxelEarth.GpuPool.DirtyRanges`
   (15 assertions over all five interval cases) rather than by four quiet legs.

8. **Fixing the consumer can break something that was load-bearing upstream.**
   `RecomputeDesiredSet` relaxes its admission cutoff to `DBL_MAX` whenever the
   pending queue is short. That was a proxy for "there is spare capacity", and it
   was only ever correct because the queue was short from starvation. Making the
   consumer fast made the queue permanently short, so the cutoff is permanently
   disabled and admission floods — 22,300 records/s against ~800 loading. **A
   proxy metric encodes the regime it was written in.**

9. **The bottleneck migrated four times in one session** — apply cost → result
   queue backlog → unload drain → admission enumeration — and at each step the
   next thing to build looked obvious and was wrong. Re-baseline after every fix
   is not caution, it is the only way this converges.

10. **The harness has to enforce the discipline, not document it.**
    `voxel-run-leg.ps1` silently truncated flight legs (its settle rule fires
    during the preflight) and reported success. It now refuses `-VoxelPerfFlight=`
    outright. Every rule in this file that survived did so because something
    threw an error, not because someone remembered.

## What this means for T4-1

The premise holds and is now measured in-engine rather than inferred from a
bench: the GPU finishes a chunk in ~12 ms and waits ~128 ms to be picked up, at
~11 jobs in flight against a cap of 256. There is real idle capacity.

Two things changed about how to spend it:

- **Speculation adds admission-side work**, and admission is now the bottleneck.
  Building a speculative enumerator onto a flooding admission path is the same
  error as building a producer multiplier while the consumer was the wall — the
  error this whole re-sequencing existed to avoid. Fix the cutoff (S2-0) or land
  T4-2 first.
- **Speculative geometry has no natural back pressure.** Residency was measured
  expanding to fill all available capacity the moment the drain lagged. Geometry
  nothing has asked for cannot be allowed to do that, so its cap is a
  correctness boundary rather than a tuning knob.

And the target has moved: converged `holes = 0` is already achieved without
speculation, so T4-1 is now aimed specifically at the transient leading-edge gap
under motion — which must be re-measured at the S1 config before its win is
stated against it.
