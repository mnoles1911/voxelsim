SETTLE DISCIPLINE, AND A RULE THAT WAS CORRECTED HERE
-----------------------------------------------------
The rule this set was started under was "any non-zero value means the frame is
not settled and must be excluded, not argued". That is right for a stationary
capture and too broad in general, and the cave frame is what exposed it:
fix-cave reports unloaded=225 and can never report anything else, because the
fixture teleports the pawn 21 m underground mid-run and surface chunks unload BY
DESIGN. Applying the rule literally there does not measure settledness, it
measures whether the fixture moved the camera -- which is already known. The
corrected rule, and the one this set is judged under:

    jobsInFlight == 0 AND pendingJobs == 0 are REQUIRED for any judged frame.
    unloaded must be 0 for a STATIONARY capture; for a fixture that deliberately
    moves the camera (teleport, flight leg), unloaded is expected to be non-zero
    and is not evidence either way. State which kind the frame is.

  fix-tundra-vista          STATIONARY  0 / 0 / 0                          56,411
  base-taiga-vista          STATIONARY  0 / 0 / 0                          42,506
  fix-taiga-vista           STATIONARY  0 / 0 / 0                          42,464

All eight report 0 undrawn chunks, so no black gap in any of these images is GPU

THE PAIRED peak loaded COUNTS ARE THEMSELVES A RESULT. Each pair settles to

TWO THINGS THAT WENT WRONG, RECORDED BECAUSE THEY NEARLY REACHED THE OUTPUT
---------------------------------------------------------------------------
1. CONTENTION. This box runs one editor at a time, and for part of this run a
   second agent was also capturing on it. Three of my captures had their editors
   terminated mid-settle -- logs stopping abruptly, no crash marker, no fatal
   line, 32 GB free. That is a scheduling collision, not a defect in the build.
   The affected frames were re-shot at FULL settle on an exclusive box rather
   than re-taken with a shorter one.

2. I MISREAD MY OWN LOG AND NEARLY DISCARDED A GOOD FRAME. settle-log.txt is
   append-only and holds one entry per ATTEMPT, so fix-tundra-vista appears
   twice: once for the killed attempt at jobsInFlight=332 pendingJobs=240, and
   once for the 600 s re-shoot at 0/0/0. A grep that matched the FIRST entry
   said the delivered frame was unsettled. It is not -- its log carries 120
   streaming samples and a final timestamp matching the screenshot's. When
   reading this file, take the LAST entry for a frame name, not the first.

The tundra site is shot at a 600 s settle rather than the 420 s the other vistas
get. At 420 s it was still at jobsInFlight=332 pendingJobs=240: it is the
3,582 m relief alpine tile and it streams far more than the others. Raising the
settle is the sanctioned response to a non-zero queue depth; arguing the frame
is not.
